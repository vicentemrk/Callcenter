1. Ruta incorrecta de la base de datos
En settings.py, la configuracion original era:
'NAME': os.environ.get('DB_NAME', 'CallCenterGamer')

Como no existía la variable de entorno DB_NAME, 
Django usaba CallCenterGamer como ruta relativa. SQLite interpretaba esa ruta como:
C:\Users\sistema\Downloads\CallCenterGamer\CallCenterGamer
Pero CallCenterGamer es una carpeta del proyecto, no un archivo de base de datos. 
Por eso SQLite generaba:
sqlite3.OperationalError: unable to open database file
La base correcta era el archivo:
C:\Users\sistema\Downloads\CallCenterGamer\db.sqlite3
se corrigio usando:
'NAME': os.environ.get('DB_NAME', str(BASE_DIR / 'db.sqlite3'))

18. Estados y prioridades de los tickets

En el proyecto, cada pregunta funciona como un ticket de atencion. Se
agregaron un estado y una prioridad para ordenar el trabajo de los tecnicos y
conocer la situacion de cada solicitud.

Estados propuestos:
- Pendiente: la pregunta fue creada, pero aun no ha sido atendida.
- En proceso: un tecnico comenzo a trabajar en la solicitud.
- Resuelto: ya se entrego una solucion al usuario.
- Cerrado: la atencion termino oficialmente.

Prioridades propuestas:
- Baja: problema menor o consulta general.
- Media: problema normal.
- Alta: dificultad importante para el usuario.
- Urgente: el servicio esta completamente bloqueado.

Flujo propuesto:

El usuario crea una pregunta
        |
        v
Estado: Pendiente
        |
        v
Un tecnico la toma
        |
        v
Estado: En proceso
        |
        v
El tecnico responde
        |
        v
Estado: Resuelto
        |
        v
Se finaliza la atencion
        |
        v
Estado: Cerrado

Implementacion realizada:
- Se agregaron los campos estado y prioridad al modelo Preguntas.
- Los valores iniciales definidos son En proceso y Baja.
- Administradores y tecnicos pueden modificar estos valores desde el panel.
- Una respuesta enviada por un administrador o tecnico marca el ticket como
  Resuelto automaticamente.
- El panel muestra el estado y la prioridad de cada ticket.
- La migracion fue creada y aplicada correctamente.

19. Logging del servidor

El logging es el sistema que crea, clasifica y dirige los logs. Un log es cada
registro individual de lo que ocurre en el servidor. El logging reemplaza los
`print` usados para
informar errores por registros con niveles como INFO, WARNING y ERROR. Servira
para investigar fallos de la IA y otros problemas del servidor sin mostrar
detalles tecnicos al usuario.

Funcionamiento propuesto:
- INFO: registra acciones normales, como el inicio de una sesion.
- WARNING: registra situaciones inusuales que no detienen la aplicacion.
- ERROR: registra operaciones que fallaron, como una consulta a la IA.
- CRITICAL: registra problemas graves que requieren atencion inmediata.

El logging funcionara como una bitacora del servidor. Permitira buscar cuando
ocurrio un problema, que operacion fallo y en que parte del sistema sucedio.
Implementacion realizada:
- Se reemplazaron los `print` de recomendaciones IA y Analytics IA.
- Los errores se registran con `logger.exception`, conservando la traza tecnica.
- Los registros se muestran en la consola durante el desarrollo.
- Tambien se guardan en `logs/callcentergamer.log`.
- Se configuraron loggers separados para `online` y `administracion`.
- No se registran contrasenas ni datos confidenciales del usuario.
- La configuracion principal esta reunida en `CallCenterGamer/settings.py`.
- La ruta del archivo se define en `LOG_FILE`, para encontrarla facilmente.

Ejemplo sencillo:
- Si falla una consulta de IA, el usuario recibe el mensaje normal de la
  aplicacion y el servidor guarda un ERROR con la causa tecnica.

Como agregar un log en el futuro:
1. Importar `logging` en el archivo.
2. Crear `logger = logging.getLogger(__name__)`.
3. Usar `logger.info(...)`, `logger.warning(...)` o `logger.exception(...)`
   segun el tipo de mensaje.

21. Optimizacion de consultas

Se revisaron las consultas de las vistas y utilidades para entender que
informacion obtiene cada una y evitar trabajo repetido.

Consultas principales y motivo:
- `Usuario.objects.get(...)`: obtiene el usuario exacto de la sesion o el
  usuario que un administrador desea modificar. Se usa `get` porque debe
  existir un solo registro.
- `Preguntas.objects.filter(...)`: obtiene las preguntas de un usuario, una
  pregunta concreta o las preguntas de un periodo. Se usa `filter` porque
  puede devolver varios registros.
- `select_related('Usuario')`: carga cada usuario junto con su pregunta en la
  misma consulta. Se usa en el panel para no consultar el usuario nuevamente
  por cada fila.
- `annotate(Count('respuesta'))`: cuenta las respuestas de cada pregunta para
  mostrar si ya fue respondida y construir las metricas.
- `aggregate(Count(...))`: calcula el total, las preguntas sin respuesta y las
  creadas durante la semana en una agregacion de la base de datos, evitando
  recalcular el mismo listado varias veces.
- `Min('respuesta__FechaHora')` con `Q`: encuentra la primera respuesta de
  administradores o tecnicos para medir el tiempo real de atencion.
- `Usuario.objects.count()`: cuenta los usuarios para la tarjeta de metricas,
  sin cargar todos sus datos en memoria.
- `prefetch_related` en recomendaciones IA: carga las respuestas de las
  preguntas resueltas en conjunto, evitando una consulta por cada pregunta
  dentro del ciclo.
- `.exists()` en formularios: comprueba si un correo ya existe sin cargar el
  usuario completo.

La optimizacion no elimina consultas necesarias; evita consultas repetidas y
mantiene el mismo resultado visible para el usuario.

Se cambió el sistema de roles

admin = True o False
tecnico = True o False
Eso permitía combinaciones confusas, por ejemplo:

admin=True, tecnico=True

Ahora se utiliza un único campo:

rol = "cliente"
rol = "tecnico"
rol = "administrador"

Así, cada usuario tiene un solo rol principal.

Ejemplos:

Cliente: puede crear Preguntas y consultar sus respuestas.
Técnico: puede revisar y responder Preguntas.
Administrador: puede gestionar usuarios y realizar acciones administrativas.

Se migraron los usuarios antiguos
La migración convierte los usuarios que ya existían:

admin=True → rol="administrador"
admin=False y tecnico=True → rol="tecnico"
Ambos valores falsos → rol="cliente"
Después de hacer la conversión, se eliminaron los campos antiguos admin y tecnico de la base de datos.
